# Smooth 30→45/60 (experimental)

## Что это

Если игра на консоли залочена на 30 fps, xHome присылает 30 кадров в секунду.
Клиент не может поднять частоту игровой логики. Он может только **показывать
больше кадров**, вставляя промежуточные между двумя decoded-кадрами.

Включение: Настройки → «Качество и буфер» → **Smooth 30→45** → target FPS 45/60.

## Как работает

1. Декодированный кадр A показывается.
2. Приходит кадр B. Клиент держит A и B в двух WebGL-текстурах.
3. Таймер с частотой target FPS рисует `mix(A, B, alpha)`, где `alpha` растёт
   от 0 до 1 за время между A и B.
4. Следующий кадр C заменяет пару, и цикл повторяется.

Это **crossfade**, а не motion compensation: векторов движения у видео нет.
Поэтому на камере, колёсах и быстро движущихся объектах будет двоение. В этом
режиме upscale делается билинейно (а не Catmull-Rom), чтобы удешевить два
полных прохода; резкость компенсируется unsharp.

## Цена

| Параметр | Значение |
|---|---|
| Задержка | +1 исходный кадр: **+33 мс** при 30 fps, +16.7 мс при 60 fps |
| Артефакты | ghosting / двойные контуры на движении |
| Игровая логика | остаётся 30 fps; стрельба/физика не ускоряются |
| GPU | дополнительный fullscreen-pass на target FPS |

HUD добавляет компонент `smooth` к `latency`, чтобы цифра не выглядела лучше,
чем есть.

## Когда включать

* Игра стабильно 30 fps, монитор 60/120/144 Гц, и вы готовы к +33 мс ради
  плавности картинки.
* Не включать для 60 fps игр: target 45 будет **хуже** источника.
* Не включать для соревновательных шутеров: задержка важнее плавности.

## Почему не FSR 3 FG

FSR 3 Frame Generation — часть рендер-пайплайна игры. Ему нужны motion vectors,
depth и jitter камеры. В H.264-потоке этого нет; клиентская интерполяция — это
приближение, а не FSR 3.
